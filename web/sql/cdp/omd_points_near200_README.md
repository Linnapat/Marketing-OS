ตั้งไว้ใน CDP (Supabase `teppen-cdp`) แล้ว สถานะ **ACTIVE — ส่งอัตโนมัติวันละครั้ง**

| | |
|---|---|
| รีเฟรชกลุ่ม | pg_cron job `omd-near200-refresh` · 04:40 UTC = **11:40 น. ไทย** ทุกวัน |
| ส่งข้อความ | CDP automation runner รอบรายวันของตัวเอง หลังกลุ่มถูกรีเฟรช |
| คนใหม่ต่อวัน | เพดาน **250 คน** (สภาวะปกติมีคนเข้าแถบใหม่ ~10–22 คน/วัน) |

## ทำไมต้อง 200 แต้ม

| ข้อมูล 12 เดือนล่าสุด (OMD) | ตัวเลข |
|---|---|
| การแลกแต้มทั้งหมด | ~840 ครั้ง |
| แลกที่ 200 แต้มพอดี | **765 ครั้ง (91%)** |
| อัตราได้แต้ม | 10 บาท = 1 แต้ม |
| บิลเฉลี่ย | 588 บาท ≈ 58 แต้ม/มื้อ |

200 คือขั้นบันไดจริงของแบรนด์ ไม่ใช่ตัวเลขที่ตั้งขึ้นเอง
คนที่ค้างอยู่ 150–199 คือคนที่ "อีกมื้อเดียวก็ถึง" — ต้นทุนการกระตุ้นต่ำที่สุดในฐาน

## ของที่สร้างไว้ใน CDP

| Segment (ทั้งแถบ) | `seg_omd_near200` | **1,878 คน** — เปลี่ยนทุกวันตามแต้มจริง |

| Automation | `auto_points_near200_omd` | **ACTIVE** · 1 ครั้ง/คน · เว้น 720 ชม. · หยุดเมื่อลูกค้ามาร้าน |
| งานรายวัน | `public.refresh_omd_near200(250)` | pg_cron 04:40 UTC |

คิวของวันนี้ไม่ใช่ยอดสะสม — ทุกเช้าฟังก์ชันจะล้างแล้วเลือกใหม่ เฉพาะคนที่ยังไม่เคยได้
เรียงคนที่ใกล้ 200 ที่สุดก่อน backlog 793 คนจึงทยอยหมดใน ~4 วัน แล้วเข้าสู่ flow ปกติ
วันละ ~10–22 คนที่เพิ่งข้ามเข้าแถบ

โปรไฟล์กลุ่มที่ส่ง: แต้มเฉลี่ย 172 · มาแล้วเฉลี่ย 2.8 ครั้ง · บิลเฉลี่ย 982 บาท
— เป็น repeater ที่มีมูลค่าสูงกว่าค่าเฉลี่ยของแบรนด์ ไม่ใช่ลูกค้าขาจร

## เรื่องที่ยังค้าง — ชื่อของรางวัล

ข้อความตอนนี้เขียนว่า "แลกรับ**ของรางวัลสมาชิก 1 สิทธิ์**" เพราะในระบบไม่มีข้อมูลว่า
200 แต้มแลกอะไรได้จริง ถ้าใส่ชื่อของจริงได้ (เช่น ของหวาน / เครื่องดื่ม) อัตราการกลับมา
จะดีกว่าคำกลาง ๆ มาก — แก้ที่ `omd_points_near200_seed.sql` แล้วรันซ้ำ

## การใช้งานประจำ

รีเฟรชรายวันทำงานเองผ่าน pg_cron ไม่ต้องรันมือ ที่เหลือคือ

```sql
-- ดูว่างานรายวันยังตั้งอยู่ และรอบล่าสุดผลเป็นอะไร
select * from cron.job;
select jobid, status, start_time, return_message
from cron.job_run_details order by start_time desc limit 5;

-- เร่งเคลียร์ backlog เร็วกว่าเพดานปกติ
select * from public.refresh_omd_near200(1000);

-- หยุดส่ง
select cron.unschedule('omd-near200-refresh');
update "Automation" set status = 'PAUSED' where id = 'auto_points_near200_omd';
```

แก้ข้อความ / เงื่อนไข Segment / cap → แก้ `omd_points_near200_seed.sql` แล้วรันซ้ำ
(ทุก statement เป็น upsert รันซ้ำได้ไม่พัง)

## วัดผลยังไง (30 วันจากวันเปิด)

เทียบ TEST_B (1,659 คน) กับ CONTROL (223 คน) ในตาราง `ab_test_membership`
ชื่อเทส `points_near200_OMD` ตัวเลขที่ต้องดู 3 ตัว:

1. **% ที่กลับมาใน 30 วัน** — ตัวชี้ขาด ต่างกันเท่าไหร่คือผลของข้อความล้วน ๆ
2. **% ที่แลกแต้มครบ 200** — บอกว่าข้อความพาไปถึงปลายทางจริงไหม
3. **ยอดใช้จ่ายเฉลี่ยต่อคน** — ระวัง cannibalization: ถ้าคนกลับมาแต่บิลเล็กลง แปลว่ามาแค่แลกของ

ถ้า lift ของข้อ 1 ต่ำกว่า 3 จุด ให้แก้ข้อความก่อน อย่าเพิ่งขยายกลุ่ม

## ก้าวถัดไปที่ยังไม่ได้ทำ

- **แต้มใกล้หมดอายุ** — ในกลุ่มนี้มี 621 คนที่แต้มจะหมดอายุใน 90 วัน
  "แต้มคุณจะหมดอายุ" แรงกว่า "อีกนิดเดียวก็ครบ" แต่ต้องมีตัวแปรวันหมดอายุในเทมเพลตก่อน
- **กลุ่มหายเกิน 90 วัน (978 คน)** — ใช้แต้มค้างเป็นเหตุผลกลับมา แต่ต้องเขียนคนละโทน
